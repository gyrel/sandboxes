# Модель безопасности

Gyrel создаётся для запуска задач агента в изолированных microVM-песочницах и хранения host credentials под контролем host-системы. Это направление реализации, а не общее заключение о безопасности. Gyrel — альфа-ПО.

## Границы доверия

- Локальный CLI подключается к daemon через сокет с ограниченными правами.
- Daemon управляет метаданными песочниц и runtime.
- VM-runtime отделяет guest-нагрузки от host-процессов.
- Новые sandboxes по умолчанию используют профиль egress `allow-all`, как и Docker `sbx`. Явные deny-правила, приоритет org deny и все fail-closed контроли по-прежнему ограничивают сетевой доступ; `deny-all` остаётся доступным.
- Provider credentials хранятся в системном хранилище host. Они не должны попадать в метаданные песочниц, SQLite или логи.

## Практика безопасной работы

- Проверяйте workspace перед передачей агенту с правом записи. Для входных данных используйте `:ro`.
- Профиль egress по умолчанию разрешает трафик. Добавляйте deny-правила или запускайте песочницу с `--policy-profile deny-all`, если задаче не нужен сетевой доступ.
- Не помещайте credentials в аргументы команд или обычные переменные среды. Используйте поддерживаемые команды host credential vault.
- Host hooks, MCP stdio servers, lifecycle-команды и writable mounts выполняются с правами соответствующего host-процесса. Используйте их только с явным одобрением и ограниченным окружением.
- Для экспериментов создавайте отдельные временные каталоги и уникальные имена песочниц. Удаляйте только ресурсы, созданные вашим запуском.

## Текущие ограничения

Gyrel пока не заявляет полную совместимость с Docker Sandboxes или завершённую production-границу безопасности. Ограниченный VM-backed lifecycle прошёл acceptance на macOS ARM64. Linux ARM64 guest-task также пережила detach/reattach managed containerd в Ubuntu Lima/QEMU с nested KVM на macOS; native Linux host и rootless-режим не квалифицированы. Windows WHP не реализован. Облачные команды (`move`, `ttl`, `volume`) вне области локальной альфы.

Опциональный профиль `--docker` запускает Docker daemon внутри guest, но вложенные операции `docker run`, `docker load`, `docker build` и Compose пока блокируются ограничениями `unshare` в текущем runtime. Это ограничение не означает, что сама VM не запускается. Host Docker socket не монтируется.

Service-secret proxy поддерживает несколько service-маршрутов на sandbox, но fault testing и независимый security review остаются открытыми. Некоторые сценарии registry и агентов не завершены или fail-closed. HTTP-условия политики смоделированы и валидируются, но live-применение HTTP в datapath `gvproxy` не проверено. Не закрыты жизненный цикл OAuth-токенов, очистка после сбоя host/питания, полное покрытие сетевых обходов и независимый внешний security review. Managed Linux launcher сейчас fail-closed завершается без `CAP_SYS_ADMIN`; это подтверждает отказ в rootless-режиме, но не поддержку rootless workload.

VM-backed lifecycle и exec-проверки прошли на macOS ARM64. Это не подтверждает полные agent-сценарии, другие платформы или все сетевые пути. Проверенные границы и ограничения компонентов описаны в разделах [требования](requirements.md), [архитектура](architecture.md), [workspace](workspaces.md), [сеть](networking.md) и [credentials](credentials.md).

В [руководстве Docker](docker.md) объяснена разница между входом в Docker account на host, доступом к registry и Docker Engine внутри песочницы.

На этой странице описаны модель безопасности и известные ограничения. Отсутствие результата проверки означает unknown или unverified, а не безопасность по умолчанию.
