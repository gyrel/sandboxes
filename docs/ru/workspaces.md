# Workspace и файлы

Workspace — это каталог host-системы, подключённый в песочницу. При подключении на запись процессы внутри гостя могут менять файлы host-системы. Добавляйте только необходимые агенту каталоги. VM-backed lifecycle и exec-проверки прошли macOS ARM64 live acceptance; сами параметры CLI не подтверждают безопасность workspace или полную agent parity на каждой платформе.

## Выберите каталоги

Текущий каталог используется как workspace по умолчанию:

```sh
cd /path/to/project
rsbx run shell .
```

Дополнительные каталоги указываются после имени агента. Суффикс `:ro` подключает каталог только для чтения:

```sh
rsbx run shell . /path/to/reference:ro
```

Флаг `--deny-write` делает подкаталог доступным только для чтения, пока родительский workspace остаётся доступным на запись:

```sh
rsbx run --deny-write ./secrets shell .
```

Если пути workspace не указаны, песочница запускается без подключённых каталогов. Файлы образа гостя при этом доступны.

## Работа в приватном клоне {#clone-mode}

`--clone` даёт агенту собственный Git-checkout вместо каталога, подключённого на запись. Исходный workspace подключается только для чтения в `/run/sandbox/source`, а агент работает в приватном клоне внутри гостя:

```sh
cd /path/to/project
rsbx run --clone shell .
```

Daemon создаёт клон с отключёнными hooks и credential helper. Как и в `sbx`, клон размещается по тому же абсолютному пути, который workspace занимает на хосте, а `origin` продолжает указывать на read-only источник (`/run/sandbox/source`), поэтому агент может сравнивать свою работу с оригиналом.

Пока песочница запущена, CLI добавляет в ваш репозиторий host-remote `sandbox-<name>`. Он указывает на endpoint host-loopback, который обслуживает guest Git daemon (только upload-pack), и выглядит как `git://127.0.0.1:<port>/<token>/<repository>`, поэтому коммиты агента можно забрать из песочницы. Токен случайный для каждой песочницы, живёт только пока она существует, перегенерируется при каждом старте и никогда не попадает в логи:

```sh
git fetch sandbox-api
git log --oneline sandbox-api/HEAD
```

Забранные ветки зеркалируются дважды: в `refs/remotes/sandbox-<name>/*` и в `refs/sandboxes/<name>/*`. Зеркало переживает удаление, поэтому `rsbx rm` предупреждает, что коммиты, оставшиеся только в клоне, теряются, и как восстановить забранный: `git branch LOCAL refs/sandboxes/<name>/BRANCH`.

`rsbx stop` снимает endpoint и очищает его в сохранённой песочнице; `rsbx start` публикует его заново, возможно на другом порту, и CLI обновляет URL remote. `rsbx rm` удаляет созданный им remote. Remote, URL которого вы изменили вручную, сохраняется с явной ошибкой вместо перезаписи.

У режима клона узкие требования, иначе он завершается fail closed:

- ровно один workspace, и это должен быть настоящий Git-репозиторий — каталог с файлом `.git` (linked worktree) отклоняется;
- образ должен содержать рабочий клиент `git` и `git daemon`;
- существующий непустой каталог назначения отклоняется, а не переиспользуется.

## Копирование файлов

В команде `rsbx cp` ровно одна сторона должна указывать путь внутри sandbox. Guest-пути должны быть абсолютными:

```sh
rsbx cp ./result.json build:/tmp/result.json
rsbx cp build:/tmp/report.txt ./report.txt
```

Команда копирует обычные файлы и каталоги. Символические ссылки, hard links и специальные файлы по умолчанию запрещены. Флаг `-L` следует по исходной ссылке верхнего уровня; если источник находится внутри workspace, цель ссылки должна оставаться в этом workspace. Вложенные ссылки по-прежнему запрещены.

## Повторный запуск именованной песочницы

`rsbx run --name NAME` повторно использует песочницу и при необходимости запускает её. Явное отличие набора workspace или режима чтения/записи вызывает ошибку, а не скрытую замену подключений. Для другого набора путей задайте новое имя.

## Ограничения

Workspace напрямую открывает гостю доступ к файлам host-системы. Read-only подключение запрещает запись через него, но не скрывает данные из образа гостя и не защищает тот же путь, подключённый на запись отдельно. Read-only подключения запрашивают у гостевого runtime рекурсивный read-only (`rbind:ro:rro`), поэтому вложенный submount внутри репозитория не остаётся молча доступным на запись; если гость отвергает опцию, создание падает, а не откатывается к более слабому mount. Режим клона проверен end-to-end на owned macOS ARM64 VM (create, read-only источник, host fetch, stop/start, delete). Очистка после сбоя host и широкая adversarial-проверка файловых операций не завершены. Перед подключением чувствительных данных прочитайте [руководство по безопасности](security.md).
